# Ось изменений (Axis of Change)

Обучающий материал для менти. Разбираем термин на примере CLI `opsctl` с **тремя** ортогональными осями — файлы [`3axisOpsctl-problem.ts`](./3axisOpsctl-problem.ts) и [`3axisOpsctl-solution.ts`](./3axisOpsctl-solution.ts).

Цель текста — не «запомнить определение», а научиться **видеть**, где система будет расти, и проектировать так, чтобы рост не превращался в комбинаторный ад и техдолг.

---

## 1. Что такое «ось изменений»

### Короткое определение

**Ось изменений** — это самостоятельная причина, по которой код (класс, модуль, сервис) приходится менять. Если у сущности две независимые причины меняться, у неё две оси.

Термин пришёл из формулировки Single Responsibility Principle у Роберта Мартина:

> *A class should have only one reason to change.*  
> Каждая ответственность — это **axis of change**. Когда требования меняются, изменение проявляется через смену ответственности у классов.

Важная оговорка того же автора:

> *An axis of change is an axis of change only if the changes actually occur.*  
> Ось — это не фантазия о «возможном когда-нибудь», а **реальное** направление эволюции, которое уже видно или обоснованно ожидается.

В архитектуре рядом живут близкие формулировки:

- **reason to change** (SRP) — «зачем трогаем этот модуль»;
- **axis / dimension of variability** — «по какому измерению размножаются варианты»;
- **axis of volatility** — «что нестабильно» (декомпозиция по изменчивости, а не только по функциям).

Для практики достаточно рабочей формулы:

> **Ось изменений = независимое измерение вариативности, которое будет расширяться по своей логике и по своим причинам.**

### Геометрическая аналогия

В координатах оси независимы: сдвинули `x` — `y` не обязан меняться. В коде то же самое:

| Геометрия | Софт |
| --------- | ---- |
| Ось X | «что собираем» (логи / метрики / конфиги) |
| Ось Y | «куда шлём» (file / stdout / HTTP / SSH) |
| Ось Z | «как упаковываем» (plain / gzip / archive) |

Движение вдоль одной оси **не должно** требовать правок во всех точках других осей. Если требует — оси склеены неправильно (наследованием «гибридов» или одним god-методом).

### Бытовая аналогия: кофейня

Уже знакомая из [README](./README.md) картина:

- меню напитков меняется, когда приходит новый бариста-рецептёр;
- каналы выдачи меняются, когда открывают доставку или киоск;
- способ упаковки (стакан / термопакет / набор с салфетками) меняется, когда меняется логистика.

Это **три оси**. В жизни никто не заводит сущность «Капучино-В-Термопакете-Курьеру-На-Велосипеде» как отдельный вид напитка. Заказ **собирает** три решения. В коде `3axisOpsctl` — то же: `ExportJob` + `PayloadCodec` + `DeliveryChannel`.

### Аналогия с кубом

С двумя осями получается **таблица** (плоскость): `дамп × канал`.  
С тремя — **куб**: `дамп × кодек × канал`.

Каждая новая точка на одной оси размножает **все грани** куба, если вы моделируете комбинации классами или вложенными `if`. Поэтому третья ось в `3axisOpsctl` — не «ещё один enum», а качественный скачок боли: с `3×4=12` к `3×4×3=36`.

## 2. Зачем понимать этот термин

Понимание осей — это не академизм. Это способ заранее ответить на вопрос:

> «Когда продукт попросит ещё один вариант, сколько мест в коде я потрогаю?»

### Практическая польза

1. **Предсказуемая стоимость фичи**  
   Без осей: «добавить gzip» = пройти все комбинации дамп×канал (или все ветки god-команды).  
   С осями: «добавить `GzipCodec`» = один класс + одна ветка в фабрике кодеков.

2. **Меньше сюрпризов при code review**  
   Ревьюер спрашивает не «красиво ли», а «по какой оси растём и не склеили ли мы две оси в один дифф».

3. **Тестируемость**  
   Кодек тестируется без HTTP. Канал — без `journalctl`. Дамп — без gzip. Пока оси свалены в один метод, юнит-тесты превращаются в интеграционные мини-сценарии на каждый угол куба.

4. **Разделение ответственности людей и команд**  
   Часто оси совпадают с зонами владения: платформа доставки vs домен диагностики vs security/шифрование. Склеенный код = склеенные релизы и конфликты в одном файле.

5. **Язык для разговора с ментором / командой**  
   Вместо «тут плохо» — «здесь две оси склеены наследованием, рост мультипликативный». Это ускоряет согласованные рефакторинги.

6. **Защита от ложной декомпозиции**  
   Не всё, что «можно выделить», является осью. Если изменение никогда не происходит независимо — вынос в иерархию даёт косвенность без выигрыша. Термин учит **не** абстрагировать «на будущее» в вакууме.

### Когда термин особенно полезен

- проектируете CLI, SDK, плагины, пайплайны с флагами «тип × формат × транспорт»;
- видите имена вроде `LogsGzipToHttpExport`;
- фабрика — это `switch` по составному ключу `"logs:gzip:http"`;
- в одном методе вложены три уровня `if` по разным enum;
- «особый случай» смешивает оси в одной ветке (`gzip && configs && http`).

Именно это показано в проблемном файле `3axisOpsctl`.

## 3. Алгоритм: как выделять оси изменений

Ниже — пошаговый метод. Его можно применять на дизайн-сессии, на рефакторинге и на ревью.

### Шаг 0. Зафиксировать сценарий целиком

Опишите пользовательский поток одной фразой:

> `opsctl dump` собирает диагностику, упаковывает её и доставляет куда указали флагами.

Пока нет целого сценария, оси легко перепутать с шагами алгоритма.

### Шаг 1. Выписать вопросы «что может измениться независимо»

Задайте три семейства вопросов (похожи на оси волатильности):

| Вопрос | Пример ответа в opsctl |
| ------ | ---------------------- |
| Что меняется у **одного** клиента со временем? | Сначала только логи, потом метрики и конфиги |
| Что **различается** между сценариями «в один момент»? | Один прогон — file, другой — SSH |
| Что меняется по **другой** причине / другим людям? | Команда infra добавляет S3; security — encrypt-кодек |

Если два пункта меняются по **разным** причинам — это кандидаты в разные оси.

### Шаг 2. Назвать оси глаголами/предметами, а не классами

Хорошие имена осей для opsctl:

1. **Что снимаем** — Dump / ExportJob  
2. **Куда шлём** — Channel / Delivery  
3. **Как упаковываем** — Codec / Packing  

Плохие имена: «Helper», «Manager», «Utils» — они не описывают измерение изменчивости.

### Шаг 3. Проверить ортогональность (независимость)

Для каждой пары осей спросите:

> «Могу ли я добавить вариант на оси A, **не** зная и **не** трогая варианты оси B?»

В `3axisOpsctl`:

- новый `TracesDump` не должен знать про gzip;  
- новый `ZstdCodec` не должен знать про SSH;  
- новый `S3Channel` не должен знать, логи это или метрики.

Если для нового варианта **обязательно** править чужую ось — либо оси не ортогональны, либо контракт между ними дырявый (и это отдельная проблема интерфейса).

### Шаг 4. Посчитать комбинаторику «как есть»

Запишите:

```
стоимость без разделения ≈ |A| × |B| × |C|   (классы или ветки)
стоимость с разделением  ≈ |A| + |B| + |C|   (плюс тонкая склейка)
```

Для текущего opsctl: `3×4×3 = 36` vs `3+4+3 = 10`.  
Дальше прикиньте прирост:

| Добавили | Без осей | С осями |
| -------- | -------- | ------- |
| TracesDump | +12 классов | +1 класс |
| S3Channel | +9 | +1 |
| ZstdCodec | +12 | +1 |

Если прирост «без разделения» уже неприятный на бумаге — оси пора выделять, даже если сейчас «ещё терпимо».

### Шаг 5. Отделить «ось» от «шага пайплайна»

Не каждое действие — ось. В solution есть пайплайн:

```text
collect → prepare → pack → send
```

Шаги — это **порядок работы**. Оси — это **семейства взаимозаменяемых реализаций** шагов (или ролей):

- семейство `collect` → Dump;  
- семейство `pack` → Codec;  
- семейство `send` → Channel;  
- `prepare` может остаться хуком внутри Dump (как redaction у конфигов), если не растёт своим независимым каталогом вариантов.

Правило: **ось появляется, когда у шага появляется своё ветвящееся семейство вариантов.**

### Шаг 6. Проверить критерий «изменения реально будут»

Спросите честно:

- есть ли уже второй вариант?  
- есть ли тикет / roadmap / запрос клиента?  
- меняют ли это разные люди?

Если ось гипотетическая («а вдруг понадобится 15 форматов»), не стройте иерархию заранее. Оставьте простой код и **зафиксируйте гипотезу**: «если появится третий кодек — вынесем». Преждевременный Bridge/Strategy — тоже техдолг, только со знаком «complexity».

### Шаг 7. Выбрать способ склейки осей

Когда оси найдены:

1. Каждая ось → свой интерфейс / иерархия.  
2. Склейка → **композиция** (ссылки), не наследование гибридов.  
3. Точка сборки (CLI flags, DI, фабрика) знает все оси, но **ветвит по одной оси за раз**.

В `3axisOpsctl-solution.ts` это `createCodec` + `createChannel` + `createExportJob` → `wireFromFlags`. Сумма веток, не произведение case'ов.

### Шаг 8. Регрессионный тест мышления

После выделения осей прогоните мысленный сценарий:

1. Добавить вариант на оси A — дифф только в иерархии A и её фабрике.  
2. Добавить вариант на оси B — аналогично.  
3. Собрать новую комбинацию A×B×C — **без** нового класса-гибрида.  
4. Особый случай на пересечении — не прятать в чужую ось; либо явная политика снаружи, либо осознанное расширение контракта.

Если сценарий 1–3 ломается — оси выделены неправильно.

### Мини-чеклист на ревью PR

- [ ] В именах классов есть склейка осей (`XToY`, `XViaYWithZ`)?  
- [ ] В одном `switch` составной ключ из нескольких enum?  
- [ ] В одной ветке условия из разных осей (`codec && dump && channel`)?  
- [ ] Копипаста одного и того же `collect` / `pack` / `send` по «срезам» матрицы?  
- [ ] Новый вариант требует правок «по всему кубу»?

Любой «да» — сигнал искать оси.

## 4. Влияние на архитектуру решения

### От «толстой» иерархии к нескольким тонким

Без осознания осей типичны два тупика (оба в problem-файле).

**Тупик A — комбинаторное наследование**

```text
DiagnosticExport
  ├── LogsPlainToFileExport
  ├── LogsPlainToHttpExport
  ├── LogsGzipToFileExport
  ├── LogsGzipToHttpExport
  ├── MetricsArchiveToSshExport
  └── … ещё десятки гибридов
```

Архитектурный смысл потерян: класс отвечает сразу за три измерения. Имя класса — это координата в кубе, а не ответственность.

**Тупик B — god-диспетчер**

Один метод знает все оси. Цикломатическая сложность растёт как произведение. Тесты и «особые случаи» живут в одной каше; оси начинают **протекать** друг в друга (в problem: `gzip && configs` внутри ветки HTTP).

**Решение — аддитивная архитектура**

```text
ExportJob (что)          PayloadCodec (как упаковать)     DeliveryChannel (куда)
  ├── Logs                 ├── Plain                        ├── File
  ├── Metrics              ├── Gzip                         ├── Stdout
  └── Configs              └── Archive                      ├── Http
                                                            └── Ssh

                 ExportJob ──держит──► codec + channel
```

Классический Bridge связывает **две** иерархии. Третья ось в том же духе «вклеивается» композицией: задание держит и канал, и кодек. По роли кодек часто похож на Strategy — и это нормально: Bridge и Strategy здесь **соседи**, не конкуренты.

### Что меняется в свойствах системы

| Свойство | Склеенные оси | Разделённые оси |
| -------- | ------------- | --------------- |
| Рост | мультипликативный `O(∏ nᵢ)` | аддитивный `O(∑ nᵢ)` |
| Место изменения | «все комбинации» | одна иерархия |
| Контракты | размыты, протекают | явные интерфейсы между осями |
| Сборка вариантов | compile-time классы / огромный switch | runtime composition |
| Точка знания обо всех осях | размазана по листьям | сосредоточена в тонкой фабрике/CLI |

### Влияние на границы модулей

Ось — хороший кандидат на **границу пакета/папки/сервиса**:

- `dumps/` — кто собирает;  
- `codecs/` — кто упаковывает;  
- `channels/` — кто доставляет;  
- `cli/` или `wiring/` — кто склеивает.

Так архитектура отражает модель изменений, а не случайную раскладку файлов «по удобству автора первого коммита».

### Влияние на интерфейсы

Разделение осей заставляет явно решить:

- что кодек получает на вход (`DiagnosticPayload` vs сырые байты);  
- знает ли канал про Content-Encoding;  
- где живёт redaction (хук `prepare` у Dump, а не ветка в HTTP).

Плохой интерфейс снова склеит оси («канал принимает dumpKind и сам решает, как жать»). Хороший интерфейс оставляет оси независимыми и переносит политику склейки наверх.

### Когда не тащить тяжёлую архитектуру

Если реально стабильны одна комбинация и пара `if` — достаточно простого кода. Ось как мыслительный инструмент всё равно полезна: вы **осознанно** принимаете долг «пока не выделяем» и знаете триггер рефакторинга (третий кодек, второй канал, копипаста и т.д.).

## 5. Поэтапное развитие системы и технический долг

Оси редко видны в день нуля. Типичная история продукта — и типичный путь техдолга.

### Фаза 1. «Нам нужен только один сценарий»

```text
собрать логи → записать в файл
```

Одна функция, всё ок. Осей формально нет — нет вариативности.

**Долг:** нулевой (или микроскопический). Усложнять рано.

### Фаза 2. Появляется вторая ось — ещё терпимо

```text
логи | метрики  ×  file | http
```

Кто-то делает `LogsToFile`, `LogsToHttp`, `MetricsToFile`… или один класс с двумя `if`. На 2×2 боль слабая, ревью «проглатывает».

**Долг:** скрытый. Комбинаторика ещё маленькая, но **модель уже склеенная**. Именно здесь чаще всего принимают решение «потом разберём», которое потом дорого.

### Фаза 3. Третья ось — боль становится кубической

Добавляют gzip/archive «потому что файлы большие» и кладут упаковку:

- либо внутрь каждого гибридного класса (копипаста `pack`);  
- либо третьим уровнем `if` в god-команде;  
- либо в «особые случаи» на пересечении (`gzip+http+configs`).

Это состояние `3axisOpsctl-problem.ts`.

**Долг уже явный:**

- матрица/куб комбинаций с дырами («забыли MetricsPlainToStdout» — ловится в рантайме);  
- стоимость любой фичи = произведение размеров других осей;  
- тесты не покрывают углы куба;  
- страх трогать файл = замедление фич.

### Фаза 4. «Ещё чуть-чуть» без смены модели

Добавляют Traces, S3, zstd, encrypt «потому что срочно». Каждый хотфикс увеличивает поверхность копипасты. Долг растёт **нелинейно**: не +1 класс, а + (произведение остальных).

Метафора: долг по кредитке с процентами. Каждый новый вариант — не платёж по телу, а новые проценты на старую склейку.

### Фаза 5. Рефакторинг по осям (или переписывание куска)

Выделяют иерархии, переносят поведение, чинят контракты, переписывают фабрику. Дифф большой, но дальше рост снова линейный — как в `3axisOpsctl-solution.ts`.

**Цена опоздания** = сумма всех гибридов/веток, которые пришлось понимать и мигрировать, плюс риск регрессий на «особых случаях», где оси уже перемешались.

### Как оси связаны с типами техдолга

| Симптом долга | Связь с осями |
| ------------- | ------------- |
| Копипаста | одна ответственность размножена по срезам куба |
| Fragile / Rigidity (Мартин) | изменение по одной оси ломает другие |
| God object | все оси в одном месте знания |
| Shotgun surgery | одна фича = правки во многих гибридах |
| Feature envy / mixed concerns | ветка канала знает про dump+codec |
| Дыры в матрице | забытые комбинации как runtime-ошибки |
| Медленные тесты / их отсутствие | нельзя тестировать ось изолированно |

### Стратегия здорового поэтапного развития

Не нужно строить идеальный Bridge в первый день. Нужно **вести учёт осей** по мере роста:

1. **День 0:** простой код, но в комментарии/ADR зафиксировать: «оси пока не выделяем».  
2. **Появление 2-го независимого варианта:** решить — оставляем `if` или сразу интерфейс.  
3. **Появление 3-го варианта или второй оси:** это триггер разделения.  
4. **Появление третьей оси:** почти всегда пора к композиции иерархий (как в 3axisOpsctl), иначе куб съест вас.  
5. **Запрет на «особый случай» в чужой оси:** пересечения оформлять явно на уровне wiring/политики.

Правило ментора:

> Растите систему **аддитивно по осям**, даже если сегодня ось представлена одним классом. Не растите **матрицу комбинаций**.

Один `GzipCodec` сегодня лучше, чем gzip, скопированный в четыре `*To*` класса «на потом вынесем».

### Анти-паттерн «абстракция впрок»

Обратный долг тоже бывает: три интерфейса, две фабрики и DI на систему с одним сценарием. Тогда команда платит сложностью чтения без оплаты изменчивостью.

Критерий баланса — снова определение оси:

> Выделяй ось, когда изменения **уже происходят** или **неизбежны по продуктовым сигналам**, а не когда «вдруг пригодится».

## 6. Разбор 3axisOpsctl как учебный кейс

### Три оси в задаче

| # | Ось | Вопрос продукта | Типы | Иерархия в solution |
| - | --- | --------------- | ---- | ------------------- |
| 1 | Dump | Что снимаем с хоста? | logs / metrics / configs | `ExportJob` |
| 2 | Channel | Куда доставляем пакет? | file / stdout / http / ssh | `DeliveryChannel` |
| 3 | Codec | Как готовим байты? | plain / gzip / archive | `PayloadCodec` |

Ортогональность: «упаковать gzip» не зависит от того, логи это или метрики, и не зависит от того, уйдёт ли пакет в файл или в HTTP.

### Что ломается в problem

1. Имена классов кричат о склейке: `LogsGzipToHttpExport`.  
2. `collect` / `pack` / `send` копируются по срезам куба.  
3. Фабрика ключует `"dump:codec:channel"` — таблица произведения.  
4. God-команда смешивает оси в одной ветке HTTP.  
5. Недостающие комбинации — ошибка рантайма, не структуры кода.

### Что чинит solution

1. Каждая ось — свой контракт и свои классы.  
2. `ExportJob` держит `codec` и `channel` (композиция).  
3. Фабрики ветвят **по одной оси**.  
4. `setChannel` / `setCodec` показывают: оси переключаются у живого объекта без нового гибрида.  
5. Рост: новый дамп / канал / кодек = **+1**, а не **+(произведение других)**.

### Чему учит кейс менти

- Ось — это не «ещё один enum в том же классе», а **направление независимого роста**.  
- Две оси → классический Bridge; три и больше → несколько иерархий + композиция (иногда Strategy рядом).  
- Боль растёт с произведением; архитектура должна переводить её в сумму.  
- Техдолг часто = отложенное признание новой оси при поэтапном развитии продукта.

## 7. Шпаргалка на одну страницу

**Определение:** ось изменений — независимое измерение, по которому система реально (или обоснованно скоро) будет расширяться.

**Польза:** предсказуемая стоимость фич, изоляция тестов, понятный язык ревью, меньше комбинаторного долга.

**Как найти:**

1. Опиши сценарий.  
2. Выпиши независимые причины менять код.  
3. Назови оси.  
4. Проверь ортогональность.  
5. Сравни `|A|×|B|×|C|` vs `|A|+|B|+|C|`.  
6. Отдели оси от шагов пайплайна.  
7. Не выделяй гипотетические оси.  
8. Склеивай композицией; фабрика — сумма, не произведение.

**Архитектура:** одна иерархия на ось; клиент/CLI собирает комбинацию; пересечения не прятать в чужие ветки.

**Техдолг:** склейка осей на ранней фазе кажется дешёвой; с третьей осью цена становится кубической. Платите разделением вовремя — или процентами на каждом новом варианте.

1. Откройте [`3axisOpsctl-problem.ts`](./3axisOpsctl-problem.ts) и выпишите все места, где оси склеены (имена, копипаста, составной switch, смешанная ветка).  
2. В [`3axisOpsctl-solution.ts`](./3axisOpsctl-solution.ts) проследите путь `wireFromFlags` → `run` и отметьте, какая ось отвечает за какой шаг.  
3. Добавьте на бумаге четвёртую ось (например, `encrypt: none | age`). Оцените стоимость в problem-модели и в solution-модели.
