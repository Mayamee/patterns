# Паттерн Bridge (Мост)

Структурный паттерн: разделяет одну «толстую» иерархию на **две независимые** — абстракцию (что делаем) и реализацию (как/куда доставляем) — и связывает их композицией, а не наследованием.

Идея в одной фразе: **пусть две оси изменений размножаются отдельно (A + B классов), а не как их произведение (A × B классов).**

---

## Какую задачу решает

Паттерн нужен, когда у объекта есть **минимум две независимые причины меняться**, и попытка выразить все комбинации через наследование (или через лес `if/else`) приводит к комбинаторному взрыву.

Типичная постановка:

- есть семейство высокоуровневых операций (абстракция);
- есть семейство низкоуровневых способов их выполнить (реализация);
- обе оси будут расти со временем;
- клиенту нужна возможность собрать любую пару «операция × способ» без новой подклассы на каждую пару.

Bridge решает это так:

1. Абстракция держит ссылку на интерфейс реализации.
2. Высокоуровневая логика живёт в иерархии абстракции.
3. Платформенные/транспортные/форматные детали живут в иерархии реализации.
4. Новая операция или новый способ добавляются **по одной оси**, не трогая все комбинации.

---

## Аналогия из жизни

Пульт и телевизор — классика, но ближе к разработке такая бытовая картина.

**Кофейня:**

- меню напитков: эспрессо, капучино, раф (что готовим);
- каналы выдачи: у стойки, в зал, самовывоз, доставка курьером (как отдаём).

Если моделировать «всё наследованием», появятся классы вроде `КапучиноСамовывоз`, `РафДоставка`, `ЭспрессоВЗал`… Добавили новый напиток — размножили все каналы. Добавили канал «в приложение» — размножили все напитки.

В жизни никто так не делает: бариста готовит напиток по рецепту, а отдельный процесс отвечает за выдачу. Рецепт и канал выдачи связаны **мостом** (заказом), а не гибридными сущностями «напиток-доставка».

В коде то же самое: CLI-команда экспорта логов не должна знать детали HTTP webhook, а webhook не должен знать, как собираются метрики процесса.

## Класс задач, который решает паттерн

Практический класс: **CLI-утилита операционной диагностики**, у которой независимо растут:

| Ось A — что экспортируем | Ось B — куда/как доставляем |
| ------------------------ | --------------------------- |
| системные логи           | локальный файл              |
| метрики процессов        | stdout / pipe               |
| снимок конфигов          | HTTP webhook                |
| …новые дампы             | SSH remote path             |

Без моста получается либо:

- `3 × 4 = 12` классов (`LogsToFile`, `LogsToHttp`, `MetricsToSsh`…),
- либо один «бог-класс» с вложенными `if` по типу дампа и каналу доставки.

С мостом: иерархия `ExportJob` + иерархия `DeliveryChannel`, любая комбинация собирается в рантайме.

Другие задачи того же класса:

- UI-контрол × рендер-бэкенд (Canvas / SVG / native);
- документ-редактор × формат хранения (локальный диск / облако / encrypted store);
- платёжный сценарий × платёжный шлюз;
- миграция данных × драйвер СУБД.

Общий признак: **две (и больше) ортогональные оси вариативности**.

## Признаки применимости

Имеет смысл смотреть в сторону Bridge, если:

1. **Комбинаторный взрыв подклассов** — число классов ≈ произведение вариантов по осям.
2. **Две оси меняются по разным причинам и разным людям/командам** (бизнес-операции vs инфраструктура доставки).
3. Абстракцию нужно расширять **без перекомпиляции/переписывания** всех реализаций и наоборот.
4. Хочется переключать реализацию у уже созданной абстракции (например, dry-run пишет в stdout, prod — в webhook).
5. Наследование используется, чтобы «подмешать» второе измерение (`LocalLogsExporter extends LogsExporter`), хотя измерение не является уточнением типа, а отдельной ответственностью.
6. В коде уже видны **вложенные ветвления** вида «если дамп X и канал Y».

Не каждый «интерфейс + реализация» — это Bridge. Если реализация одна и не ветвится своей иерархией, это обычная инверсия зависимостей, не мост.

## Структура (кратко)

```
Abstraction          ──────────────►  Implementation
  (ExportJob)                         (DeliveryChannel)
       ▲                                     ▲
       │                                     │
 RefinedAbstraction                   ConcreteImplementor
 (LogsExportJob, …)                   (FileChannel, HttpChannel, …)
```

- **Abstraction** — высокоуровневый API для клиента; делегирует низкоуровневую работу.
- **Refined Abstraction** — варианты бизнес-сценария.
- **Implementation** — интерфейс низкоуровневых операций.
- **Concrete Implementor** — конкретные способы выполнения.

Связь всегда **композиция / агрегация**, не наследование между осями.

---

## Минусы паттерна

1. **Больше сущностей и косвенности** — вместо пары понятных классов появляются две иерархии и точка сборки. Для одной стабильной комбинации это overkill.
2. **Сложнее читать с ходу** — поток управления прыгает между абстракцией и реализацией; без хороших имён легко потеряться.
3. **Риск «дырявой абстракции»** — если разным реализациям нужны принципиально разные операции, общий интерфейс либо раздувается, либо начинает врать.
4. **Не лечит лишние оси** — три независимых измерения (`формат × канал × сжатие`) одним мостом не закрыть; понадобятся дополнительные выделения (иногда Strategy внутри Implementor и т.п.).
5. **Легко спутать со Strategy** и применить не ту ментальную модель (см. ниже).

Правило большого пальца: Bridge окупается, когда обе оси **реально** будут расти. Если вторая ось — один `if` навсегда, мост рано.

## Отличие от Strategy (с примером)

Оба паттерна используют композицию и делегирование. Разница в **числе и роли** изменяемых иерархий.

| | Strategy | Bridge |
| --- | --- | --- |
| Цель | подменить алгоритм у контекста | развязать две оси развития |
| Иерархии | обычно одна семья стратегий | две: Abstraction и Implementation |
| Клиент думает | «какой алгоритм выбрать» | «какую абстракцию связать с какой реализацией» |
| Типичный рост | новые алгоритмы | новые абстракции **и** новые реализации |
| Когда оси связаны | одна ось (поведение) | две ортогональные оси |

### Пример на той же CLI-утилите

**Strategy** — внутри уже выбранного экспорта логов меняем только алгоритм сжатия:

```ts
// Одна ось: алгоритм. Контекст стабилен.
interface CompressionStrategy {
  compress(bytes: Uint8Array): Uint8Array;
}

class GzipCompression implements CompressionStrategy { /* ... */ }
class ZstdCompression implements CompressionStrategy { /* ... */ }

class LogsExportJob {
  constructor(private compression: CompressionStrategy) {}
  // сбор логов один и тот же; меняется только сжатие
}
```

Здесь нет второй развивающейся иерархии «что экспортируем». Меняется семейство алгоритмов сжатия.

**Bridge** — независимо меняются и тип дампа, и канал доставки:

```ts
interface DeliveryChannel { /* реализация */ }
abstract class ExportJob {
  constructor(protected channel: DeliveryChannel) {}
}
class LogsExportJob extends ExportJob { /* абстракция */ }
class MetricsExportJob extends ExportJob { /* абстракция */ }
```

Сжатие здесь может быть деталью канала или отдельной стратегией **внутри** реализации. Но сам мост отвечает за пару «задание экспорта × канал», а не за подмену одного алгоритма.

Короткий тест:

- нужно **подменить способ сделать одно и то же** → Strategy;
- нужно **дать двум иерархиям расти независимо** → Bridge;
- иногда внутри Bridge-реализации всё равно живут Strategy (сжатие, сериализация) — паттерны не враги.
